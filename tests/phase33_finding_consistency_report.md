# Phase 33 - Finding Consistency Report

This report evaluates the uniformity of findings generated by the 30 active modules.

## 1. Schema Adherence
**Status: PASS**
All 30 scanner modules utilize the unified `ScannerModule.make_finding()` method in `base.py`.
- No module manually constructs finding dictionaries.
- Required fields (`name`, `severity`, `description`, `evidence`, `confidence`, `category`) are universally populated.
- Supplemental fields (`owasp`, `compliance`, `remediation`, `impact`, `cvss`) either have explicit values or are automatically populated via the `COMPLIANCE_MAP` and `IMPACT_MAP` data dictionaries.

## 2. Severity Classification Consistency
**Status: PASS**
The scanner engine uses a strict hierarchy: `Critical`, `High`, `Medium`, `Low`, `Informational`, `Passed`.
- **Critical**: Reserved exclusively for direct credential exposure (e.g., exposed `.env`, AWS keys, Stripe keys, database dumps).
- **High**: Used for issues providing direct attack vectors (e.g., exposed `.git`, Wildcard CORS with credentials, insecure form actions, missing CSP, deprecated TLS).
- **Medium**: Used for issues that aid exploitation but aren't direct vectors (e.g., Directory indexing, missing secure flags on cookies, weak ciphers).
- **Low**: Used for minor informational disclosures or defense-in-depth gaps (e.g., verbose server banners, missing minor headers).
- **Informational**: Used for footprinting/recon data (e.g., Subdomains discovered, Cloud provider identified, WAF detected).

*Note: The audit found no instances where an informational reconnaissance finding was misclassified as High/Critical, ensuring the scoring penalty system is not polluted.*

## 3. Confidence Classification Consistency
**Status: PASS**
- **High (Default)**: Applied to deterministic findings (e.g., HTTP header is either present or missing; a `.env` file either exists or it doesn't).
- **Medium**: Applied to heuristically derived findings (e.g., "Potential IDOR path" based on URL regex; "Administrative Portal Discovered" based on keyword heuristics).
- **Low**: Applied to findings that require active verification to confirm exploitability (e.g., "Potential Missing CSRF Protection" which relies solely on the absence of a hidden token field).

## 4. Deduplication & Score Penalty Consistency
**Status: PASS**
The `scoring.py` engine successfully applies deduplication to prevent score tanking:
- **TLS Configuration**: Multiple TLS findings (e.g., "Missing HSTS", "Weak Cipher", "TLS 1.0 Supported") are grouped under the `TLS_Configuration_Issue` identity. Only the highest severity finding applies a penalty.
- **Security Headers**: Multiple missing header findings (e.g., "Missing CSP", "Missing XFO") are grouped under the `Security_Headers_Issue` identity.
- **Severity Limits**: Maximum penalties are capped per severity tier (e.g., Critical max 100, High max 30).
- **Passed Findings**: `Passed` findings correctly apply a weight of `0` and do not alter the penalty score, though they contribute to the Compliance matrix.

## 5. Cross-Module Evidence Consistency
**Status: PASS**
Evidence fields are universally truncated via `base.py` limits:
- Standard limit: `180` characters.
- Extended limit: `1000` characters (for specific findings like "Verbose Error / Stack Trace", "Source Map Leak", "Subdomains Discovered").
- Masking: Pre-truncation masking is applied consistently across all modules for AWS, Stripe, GitHub, GitLab, OpenAI, Slack, NPM, and generic Bearer tokens.

## Conclusion
The scanner exhibits high consistency in vulnerability classification, formatting, and scoring deduplication across all 69 unique findings generated by the 30 active modules.
